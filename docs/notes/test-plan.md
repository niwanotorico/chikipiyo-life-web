## 1. テストの動かしかた

### いつものテスト（ロジックの単体テスト）

```sh
npm test
```

`node --test` が `tests/*.test.js`（35 ファイル・250 件）を動かします。ブラウザは使いません。

### E2E テスト（ビルドしたサイトをブラウザで開いて確かめる）

はじめの 1 回だけ、テスト用ブラウザ（Chromium）を入れます。

```sh
npm install
npx playwright install chromium
```

そのあとは、これだけです。

```sh
npm run test:e2e
```

- 自動で `npm run build` → `vite preview` をして、**ビルド済みのサイト** に対してテストします（開発サーバーではありません）。
- 同時に GitHub Pages と同じサブパス（`--base /chikipiyo-life-web/`）のビルドも `dist-pages/` に作って確かめます。
- 時間の目安：ふつうの PC で 10〜20 分。GPU を使わないソフトウェア描画（SwiftShader）なので 3D がとても遅いためです。
- 失敗したときは `npm run test:e2e:report` で結果の画面（スクリーンショット・動画のような操作記録つき）が開きます。

よく使う形：

```sh
npx playwright test e2e/house.spec.js          # ファイルを1つだけ
npx playwright test --project=mobile           # スマホだけ
npx playwright test -g "視点リセット"           # 名前で選ぶ
npx playwright test --headed --project=desktop # ブラウザを見ながら
```

### スクリーンショットの基準画像を作りなおす

見た目を **わざと** 変えたとき（家具を足した、色を変えた など）は、基準画像を作りなおしてコミットします。

```sh
npm run test:e2e:update
```

- 基準画像は `e2e/__screenshots__/` にあります。**Linux（GitHub Actions と同じ環境）で作ったもの** です。
- Windows / Mac では描画が少しちがうので、スクリーンショット比較（`e2e/visual.spec.js`）は自動でスキップされます。ほかのテストは動きます。
- Windows から基準画像を作りなおしたいときは、GitHub Actions の結果（Artifacts の `playwright-report`）にある `*-actual.png` を使うか、Linux 環境（WSL や Claude Code のクラウド環境）で `npm run test:e2e:update` してください。

### GitHub Actions

`.github/workflows/e2e.yml`（新しく追加。公開用の `pages.yml` とは別）が、**Pull Request のたびに** `npm test` と `npm run test:e2e` を動かします。
結果のレポートは Actions の実行ページの Artifacts（`playwright-report`）からダウンロードできます。何も公開しません。

### 2.4 調査で見つけた不具合（今回は直していません）

- **スマホ幅のピヨドリルで、画面下に浮かぶナビ（ハウス・釣り・ドリル・起こし）が、ページの内容の下にかくれてタップできない。**
  `src/drill/drill.css` で `.dq-top`（ナビが入っているヘッダー）と `.dq-main` がどちらも `position:relative; z-index:1` のため、あとにある `.dq-main` が上に描かれます。ナビは `position:fixed; z-index:20` ですが、`.dq-top` の重なり順の中に閉じこめられています。ページのいちばん下（内容がナビの後ろにない所）まで行くと見えます。
  直しかたの案：`.dq-top` の `z-index` を `.dq-main` より大きくする（例 `z-index:2`）。直したら `e2e/smoke.spec.js` の `test.fixme(isMobile, ...)` を消すと、スマホでもナビのテストが動きます。

「エラーなし」の判定：`console.error` と、ページで捕まえられなかった例外（pageerror）は 1 件でも失敗。サイト内のファイル（画像・GLB・音声・JS・CSS）が 400 以上を返したり読み込みに失敗したら失敗。
外部の Google Fonts は、届かなくてもシステムフォントに切り替わるだけなので対象外です。`console.warn`（VR が開始できない、など想定ずみの警告）は失敗にしません。

#### スクリーンショット比較を安定させるための工夫

- `Math.random` をテストの中だけ固定（`e2e/helpers.js` の `seedRandom`）。
- ハウス：描画ループが始まった瞬間に一時停止して生活時計を 0 にし（キャラは初期位置で 1〜3 秒「ひとやすみ」しているので、歩き出す前に止まる）、GLB の読み込みを待ってから、カメラを初期位置に置き、**動きの更新を止めて描画だけ続けるループ** に差しかえて撮ります（テスト側だけの操作）。
- 渓流：`?still&season=summer&camp=0`（描画ループなし・夏で固定・キャンプなし）で開き、時間を進めない `frame(0)` だけを回して撮ります。
- ドリル：日付を 2026-10-14 10:00（日本時間）に固定。CSS アニメーションは止めて撮ります。
- 許容誤差：3D は 3%、それ以外は 2%（ピクセルの色の差は 0.2 まで許す）。
- 撮るのは「画面に見えている範囲」だけ（要素だけのスクショは撮影中に画面サイズが変わり、3D が消えて写ることがあったため）。

#### テストのための設定（サイトには影響しない）

- スマホ（`mobile`）は Pixel 7 の画面幅・タッチ・UA を使い、**画素密度だけ 1** にしています。2.6 倍のままだと、ソフトウェア描画で 1 フレームに数秒かかってテストが終わらないためです。高精細画面での見た目は実機で確認します。
- WebGL は `--use-angle=swiftshader` などで GPU なしでも動かしています。

## 4. 描画性能の記録

`e2e/perf.spec.js` が毎回 `test-results/perf/house.json` と `river.json` に書き出します（GitHub Actions では Artifacts の中）。
**GPU なしのソフトウェア描画での数字** なので、時間・fps は実機よりずっと悪く出ます。比べるのは「前の記録と比べて急に増えていないか」です。
ドローコール数・三角形数・GPU 上のジオメトリ／テクスチャ数・読み込み量は、実機とほぼ同じです。

### 2026-10-14 の記録（PC 幅 1280×800、Chromium + SwiftShader、ローカル）

| 項目 | 3DPハウス | おさかな釣り | 備考 |
|---|---:|---:|---|
| 初回表示（ページを開いてから 3D が動くまで） | 約 1.9 秒 | 約 2.8 秒 | ローカル配信。ハウスはキャラの GLB まで、渓流は最初のフレームまで |
| DOMContentLoaded / load | 0.5 / 0.5 秒 | 1.1 / 2.3 秒 | |
| fps（参考） | 0.9 | 1.3 | ソフトウェア描画なので実機とは無関係。0 になったら止まっている |
| ドローコール（1 フレーム） | **477** | 239 | 影の描画＋本番の描画（渓流は水の 2 パス目も）の合計 |
| 三角形（1 フレーム） | **約 185 万** | **約 276 万** | 同上。ハウスの本番の描画だけだと約 98 万 |
| GPU 上のジオメトリ / テクスチャ / シェーダー | 292 / 7 / 13 | 153 / 5 / 22 | `renderer.info` |
| JS ヒープ | 約 73MB | 約 73MB | `performance.memory`（Chromium のみ） |
| 読み込んだデータ量 | 約 36MB（22 ファイル） | 約 8MB（14 ファイル） | ハウスは `human-room.glb` が約 27MB |
| 描画サイズ | 950×820 | 1280×800 | pixelRatio 1 |

上限（`BUDGET`）：ハウス ドローコール 1000・三角形 400 万・読み込み 80MB、渓流 ドローコール 500・三角形 550 万・読み込み 20MB（いまの約 2 倍）。
性能の記録は `perf` プロジェクトで、**ほかのテストが全部終わってから単独で** 動きます（同時に動くと CPU を取りあって数字がくるうため）。ほかのテストが失敗したときは、性能の記録はスキップされます。わざと重くするときは `e2e/perf.spec.js` の数字を見直してください。

### 改善案（今回は直していません。リストだけ）

1. **ハウスの三角形が約 98 万・ドローコール約 250**（本番の描画だけ。影も入れると 185 万・477）。`human-room.glb`（約 28MB）が大部分。Blender 側でポリゴンを減らす（Decimate）、見えない裏面・床下の部品を消す、同じ素材のメッシュを結合する、で大きく減らせそうです。スマホ・Quest での発熱・電池にも効きます。
2. **部屋の GLB を圧縮**：Draco / Meshopt 圧縮で 28MB → 数 MB にできる可能性。ただし今はデコーダを設定していない（README）ので、`GLTFLoader` に `MeshoptDecoder` を足す改修が必要（`meshoptimizer` は devDependencies にすでにある）。
3. **ハウスの起動が 1 本道**：部屋・小物・プリンを順番に `await` しているので、全部そろうまで何も出ない。部屋だけ先に出して小物は後から、にすると初回表示が早くなります（失敗にも強くなる）。
4. **影（シャドウマップ）**：ハウスは 2048、渓流は PC で 4096。動かない物の影を毎フレーム描きなおしている可能性があるので、`renderer.shadowMap.autoUpdate=false` ＋必要なときだけ `needsUpdate` にすると軽くなる。
5. **ハウスの canvas はスマホで画面より 70px 広い**（左右 35px はみ出し）。描画するピクセルが 1 割ほど多い。見た目のための意図的な設定なら、そのままで OK。
6. **index.html の importmap**（`/node_modules/three/...`）はビルド後も残っていますが、ビルド版では three が中にまとめられているので使われていません。害はありませんが、消しても動作は同じはずです（消すなら実機確認のうえで）。
