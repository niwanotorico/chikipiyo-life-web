## A1 実装結果
- 仕組み（見直し後）：`src/world/transmission.js` の台帳 `opaqueTransmissionTargets` に載せた対象だけを不透明にする。
  - 対象は「アセット・メッシュ名・親の名前・素材名・元の透過値・色」の組で特定する。どれか1つでも違えば置き換えず、警告を出す。
  - 元の素材は書き換えず、対象のメッシュだけ不透明のコピーへ差し替える。同じ素材を使う台帳外のメッシュは透過のまま残る。
  - 台帳にない透過素材（今後のガラス・カーテン・エフェクト等）は変更せず、「透過用の描き直しが有効になる」と警告だけ出す。
  - 現在の台帳は6件：部屋の本のページ4つ・テーブルのコップ、掃除機のパイプ。
- `latest-room.js`（部屋）と `action-props.js`（小物）から呼ぶ。`modeling-screen.js` の事前コンパイルは、透過素材が残っている時だけ画面外描画をする。GLBファイル自体は変更していない。
- 描画回数：779 → 508（-35%）。三角形：307万 → 199万（-35%）。食事中：797/490万 → 520/321万。見直し後も同じ値。
- 見た目：いつものカメラで最大差9/255（4ピクセル）。透過素材5か所の寄りでも最大差3〜19/255で、見て分かる差はなし。見直し前（一律方式）との差は0。
- テスト65件中64件成功（失敗1件はVR家具GLBを確認用コピーに入れていないため、今回とは無関係）。ビルド成功。本番ページはエラーなしで動作。

## 実機への影響が大きい順（ユーザーの6項目）
1. pixelRatio 最大2（＋MSAA）：ピクセルの処理量が1倍の4倍。すべてのパスに効く。
2. 描画回数456（実際は779、A1後508）：A1前は271回が透過パスだった。スマホのCPU負荷が大きい。
3. 186万三角形（実際は307万、A1後199万）：本体108万＋影91万（＋A1前は透過108万）。
4. 2048のソフトシャドウ：影パス237回・91万三角形＋全画素のぼかし処理。
5. ハンバーガー16MB：食事中だけ三角形が大きく増え、その間カクつく。読み込みも重い。
6. 部屋28MB：毎フレームへの影響は3に含まれる。読み込み時間・メモリ・パース時間の問題。

## 見た目をほぼ落とさない改善
- A1 `white` の透過を0（不透明）にする → 実装済み（台帳方式）。
- A2 ハンバーガーを1〜2万三角形へ間引く：食事中のカクつき解消、16MB→1MB未満。
- A3 コンロ・ベッド・布団・コーヒーメーカーを間引く（Decimate）：本体 約-40万、影も同じだけ減る。
- A4 GLBの圧縮（meshopt＋量子化、未使用UVの削除）：28MB→数MB、読み込みとメモリが軽くなる。
- A5 小物（コップ・本・小さな飾り）は影を落とさない：影の描画回数を減らす。
- A6 同じ色の素材をまとめる（168→数十）：描画の状態切り替えを減らす。

## 見た目とのトレードオフがある改善
- B1 モバイルだけ pixelRatio を1.5（またはFPSに応じて自動調整）：少しだけ柔らかく見える。
- B2 モバイルは影マップ1024／PCF、または影の更新を2フレームに1回：影の縁や追従が少し変わる。
- B3 動かない家具をまとめて1メッシュ化（271回→数十回）：クリック判定や扉・掃除機などの動く部分を除外する設計が必要。
- B4 部屋の影を焼き込み、リアルタイムの影はキャラクターだけ：大きく軽くなるが、焼き込み作業が必要で質感も変わる。
- B5 高DPR端末ではMSAAを切る：斜めの線がわずかにギザつく。
